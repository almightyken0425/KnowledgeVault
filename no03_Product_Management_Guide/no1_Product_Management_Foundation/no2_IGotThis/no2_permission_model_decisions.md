# 權限模型定案紀錄

> 本篇記錄 IGotThis 權限模型的定案。內容含授權的承載形態、範圍與等級、公司層開關、檢視層分享規則。由工單資料模型定案所列的範圍外依賴推導而來，每項定案附選擇理由。

## 本篇範圍

- **涵蓋:**
    - 帳號與 Role 的資料形狀
    - 授權範圍與等級的定義
    - 公司定義區的編輯權限
    - 檢視層分享與權限的優先關係
    - 關聯跨越權限邊界的顯示規則
- **不涵蓋:**
    - 工作日與假日設定
    - 檢視層其餘形態
    - 分享給公司以外的帳號
    - 登入安全與稽核紀錄
- **推導前提:**
    - 容器骨架為嚴格樹狀，一個 `Product` 只屬一個 `Team`
    - 型別定義全公司共用一份
    - 彙總正確性是本設計的核心價值

---

## 授權的承載形態

- 權限不掛帳號，掛 Role
- 帳號持有一組 Role，Role 持有授權內容
- Role 可重用，同一個 Role 可分配給多個帳號

```
帳號
├── Name
├── Role 清單     可多筆
└── 標籤          部門等分類，不影響權限

Role
├── RoleTitle
├── 範圍清單      Company 或 Team 或 Product 或 Mgmt，可多筆
├── 等級          觀看 / 回報 / 成員 / 管理
├── 公司層開關    型別維護 / 組織結構 / 權限管理
└── 標籤          分類等，不影響權限
```

- **選擇理由:**
    - 十個後端共用一個 Role → 改一次全體生效
    - 逐帳號授權的維護量隨人數線性成長
- **範圍與等級皆掛 Role 整體:**
    - 不掛範圍清單的每一項
    - 掛每一項會讓 Role 在清單上看不出用途
    - 用途不明的 Role 沒有重用價值

---

## 授權範圍定案

- 一個帳號可掛多個 Role
- 多個 Role 的授權取聯集
- 同一個位置命中多筆時取較高的等級
- 兩名成員的需求略有差異時，以共用 Role 加專屬 Role 表達

```
Role LedgerApp 開發    ─┬─→ 成員甲
Role AIMarketing 觀看  ─┘

Role LedgerApp 開發    ─┬─→ 成員乙
Role PayGate 觀看      ─┘
```

- 三個 Role 拼出兩種人 → Role 成為可組合的積木
- **一帳號一 Role 的代價:**
    - Role 數量等於權限組合數
    - 每多一名需求略異的成員就多一個一次性 Role
    - 人事異動須改動 Role 定義本身
- **不支援排除:**
    - 表達不了除某個產品以外皆可檢視
    - 排除規則會讓有效權限無法推理
    - 需要排除時改為縮小範圍清單的項目

---

## 範圍清單的項目形態

- 範圍清單的每一項可寫四種之一
    - 整個 `Company`
    - 整個 `Team`，涵蓋其下全部 `Product`
    - 整個 `Product`，涵蓋其下全部 `Mgmt`
    - 單一 `Mgmt`
- 明列與涵蓋整層可混用

```
Company IGotThis          寫進清單 → 全公司生效
├── Team Dev1             寫進清單 → Dev1 的全部產品
│   ├── Product LedgerApp     寫進清單 → 僅此產品
│   └── Product AIMarketing
└── Team Dev2
```

- 外部團隊需檢視某產品時，單獨寫該 `Product` 一項
- 此即跨團隊檢視由權限解決而非由結構解決的實作方式
- **粒度下限為 `Mgmt`:**
    - `IssueSet` 與其下不開授權
    - 檢視層的資料來源儲存形態即 `Mgmt` 清單
    - 兩處同粒度 → 權限與檢視層講同一種話
    - 再細一層會讓權限檢查點倍增
- **權限跟隨整層項目自動擴張:**
    - `Product LedgerApp` 新增 `Mgmt<Support>`
    - 寫著整個 LedgerApp 的 Role 自動涵蓋新的 `Mgmt`
- **與檢視層資料來源的方向相反:**
    - 檢視層展開後不跟隨來源，新 `Mgmt` 不自動進表
    - 權限則自動跟隨
    - 表要排哪些主題是人的決策 → 未經決策不該取得位置
    - 能否進入某產品是組織事實 → 同產品新開管理區，原團隊本就該進得去

## 等級定義

- 等級收進定義表，一列一個等級
- 內建四列標系統欄，不可刪除
- 使用者可自行加列

| 等級 | 讀 | 留言 | 建單 | 改自己的 | 改別人的 | 封存 | 改結構 | 分派 Role |
|---|---|---|---|---|---|---|---|---|
| 觀看 | 是 | 否 | 否 | 否 | 否 | 否 | 否 | 否 |
| 回報 | 是 | 是 | 是 | 是 | 否 | 否 | 否 | 否 |
| 成員 | 是 | 是 | 是 | 是 | 是 | 否 | 否 | 否 |
| 管理 | 是 | 是 | 是 | 是 | 是 | 是 | 是 | 是 |

- **各等級的預期對象:**
    - 觀看給外部利害關係人，含高階主管與客戶
    - 回報給外包與客服，可開單可追蹤，不動別人的單
    - 成員給團隊
    - 管理給產品負責人與組長
- **開關的語意:**
    - 改結構指新增 `IssueSet`、改 `Mgmt` 名稱、改 `IssueSet` 的 KEY
    - 分派 Role 指把現成的 Role 指給帳號
- **分派 Role 的兩條限制:**
    - 只能在自身範圍內分派
    - 只能給不高於自身的等級
- **選擇理由:**
    - 寫死等級撐不過第一個特殊需求
    - 純動作開關讓每次建立 Role 都要勾十幾個開關
    - 開關全開放會勾出壞組合，例如可封存卻不可讀
- 內建標系統欄加開放自建，與關聯型別定義表同一個模式

## 公司層開關

- 定義區與 `Team` 平行，範圍清單指不到它
- Role 另帶一組公司層開關
- 公司層開關不吃範圍清單，因定義全公司一份
- 不存在只維護單一產品型別的角色

| 開關 | 管的內容 |
|---|---|
| 型別維護 | 欄位、欄位組、工單型別配方、狀態流程、結案原因、關聯型別 |
| 組織結構 | 建立與刪除 `Team` 與 `Product` |
| 權限管理 | Role 定義、等級定義表、標籤群組定義 |

- **切三塊的理由:**
    - 權限管理必須獨立 → 否則可改欄位的人能自行提權
    - 組織結構獨立 → 範圍清單的最大項是 `Company`，但建立與刪除是另一回事
    - 型別維護的內容彼此相依，拆開反而難以判斷該勾哪些
- 新增 `Mgmt` 不屬公司層，歸該 `Product` 的管理級
- **分派與定義是兩件事:**
    - 管理級分派現成的 Role，限自身範圍
    - 權限管理造出新的 Role 與新的等級
- **不再細分的理由:**
    - 會改定義區的人全公司通常個位數
    - 切太細會讓建立 Role 的人不知該勾哪些
    - 日後要細分是加欄位，不動架構
- **殺傷力的認知:**
    - 改一個關聯型別的彙總開關 → 全公司母單的數字當場改變
    - 刪一個狀態 → 所有該型別的工單流程斷掉

---

## 篩選標籤

- 帳號與 Role 皆可掛標籤
- 標籤群組定義收在定義區
- 內建帳號的部門與 Role 的分類，標系統欄不可刪
- 使用者可自行加標籤群組
- 每個標籤群組帶固定的值清單，不接受自由文字
- **固定值清單的理由:**
    - 自由文字會長出工程部、工程、研發三種寫法
    - 寫法分歧 → 篩選失效
- **標籤對權限零影響:**
    - 部門不是門禁
    - 授權只看 Role 的範圍清單與等級
- **部門與 `Team` 的分工:**
    - `Team` 管權限範圍，是容器骨架的一層
    - 部門只是人事維度的標籤
    - 一名成員可屬工程部，同時被派在 Dev1 做 LedgerApp
    - Role 已能讓一群人共用權限 → 部門再參與授權即第二條路
    - 兩條路做同一件事 → 有效權限查不清楚

## 檢視層分享定案

- 表照分享，內容依接收者的權限過濾
- 被濾掉的部分顯示筆數與原因，不顯示內容
- 分享不放寬權限
- 表的資料來源跨產品跨團隊，與接收者的範圍清單不必然吻合

```
View 開發順序表
資料來源五個 Mgmt
├── LedgerApp / Requirement      接收者有權限
├── LedgerApp / Project          接收者有權限
├── AIMarketing / Requirement    接收者有權限
├── PayGate / Requirement        接收者無權限
└── PayGate / Project            接收者無權限
```

- **選擇理由:**
    - 分享放寬權限 → 任意成員拉全公司的 `Mgmt` 建表再分享 → 權限模型破功
    - 靜默過濾 → 接收者分不清是尚未排序還是無權限
    - 標出筆數只多一行提示，換掉一整類誤會
- **分享前預覽:**
    - 分享時顯示接收者會被濾掉幾筆
    - 補權限由分享者自行處理
- **分享分三級:**

| 層級 | 能做的事 |
|---|---|
| 唯讀 | 檢視，不可改任何檢視設定 |
| 可編輯 | 改排序、篩選、顯示層級、資料來源 |
| 擁有者 | 建立者，改分享對象，刪除表 |

- 可編輯層級改排序後全體檢視者同步變動，因表只有一份
- 此即排序歸屬定案所稱的共識靠分享達成
- **分享對象清單的形態:**
    - 每項可寫單一帳號、`Team`、或整個 `Company`
    - 與 Role 的範圍清單同一個模式
- **建立表的權限:**
    - 任何具備讀權限的帳號皆可建立自己的表
    - 表只讀資料，建立不影響他方

## 關聯跨越權限邊界

- 關聯指向無權限的工單時只顯示工單編號
- 標題與內容不顯示，工單不可點開
- **狀況成因:**
    - 建立關聯時只搜得到自身有權限的工單
    - 跨界的關聯來自事後撤銷權限
- **母子不受影響:**
    - 母子鏈不跨 `IssueSet` → 必在同一個 `Mgmt` 內
    - 同一個 `Mgmt` 的權限一致
- **會跨界的關聯:**
    - 主題綁定跨 `IssueSet`
    - Before 與 RelatedTo 無範圍限制

```
Issue LSPEC-142        有權限
└── Before → PAY-88    位於 PayGate，無權限
```

- **只顯示編號的取捨:**
    - 洩漏的僅為該工單存在，以及所屬 `IssueSet`
    - 編號前綴即 `IssueSet` 的 KEY → 歸屬本就藏不住
    - 業務內容完全不洩漏
    - 取得編號才能向管理者申請權限
- 該欄位配一個申請存取的動作，送往該 `Mgmt` 的管理級
- 反查方向套用同一規則
- **與檢視層過濾的差異:**
    - 檢視層被濾掉的可能數十筆 → 列編號無意義
    - 關聯欄位通常個位數 → 需要追蹤依賴
- **完全隱藏的代價:**
    - 前置依賴看不見 → 排程判斷失準
    - 甘特圖連線斷開且無任何提示

---

## 權限粒度的下限

- 權限最細到 `Mgmt`，單張工單不另設權限
- 工單不帶私密旗標，不帶額外可見名單

```
Task 母單   估點彙總 13
├── Task A  估點 5    全體可見
├── Task B  估點 3    全體可見
└── Task C  估點 5    限三人可見
```

- 母單顯示 13 → 洩漏 Task C 的存在與大小
- 母單顯示 8 → 同一張母單因人而異，數字失去意義
- 兩條路皆破壞彙總 → 彙總不可信則系統的主要價值消失
- **粒度到 `Mgmt` 與既有定案咬合:**
    - 母子不跨 `IssueSet` → 彙總鏈必在同一個 `Mgmt` 內
    - 同一個 `Mgmt` 的權限一致 → 彙總結果對全體可見者相同
- **敏感工單的出口:**
    - 另開一個 `Mgmt`，自訂其 Role 名單
    - 與主線以 RelatedTo 連結
    - 跨界顯示套用關聯跨越權限邊界的規則
- **換來的代價:**
    - 為單張敏感工單開 `Mgmt` 成本偏高
    - 缺陷常在開發階段當場發現，搬移為事後動作
    - 搬移會斷開母子關係，因母子不跨 `IssueSet`
    - 編號不隨搬移改變，此點已由工單編號定案處理
- **額外可見名單的另一個問題:**
    - 成員可逐張分享給外部帳號
    - 檢視層分享堵住的洞會從此處開回來

## 權限的儲存形態

```sql
CREATE TABLE role_def (
  name       text PRIMARY KEY,
  level      text,
  type_admin boolean,
  org_admin  boolean,
  perm_admin boolean
);

CREATE TABLE role_scope (
  role_name  text,
  scope_kind text,
  scope_id   uuid,
  PRIMARY KEY (role_name, scope_kind, scope_id)
);

CREATE TABLE account_role (
  account_id uuid,
  role_name  text,
  PRIMARY KEY (account_id, role_name)
);

CREATE TABLE level_def (
  name            text PRIMARY KEY,
  system          boolean,
  can_read        boolean,
  can_comment     boolean,
  can_create      boolean,
  can_edit_own    boolean,
  can_edit_any    boolean,
  can_archive     boolean,
  can_structure   boolean,
  can_assign_role boolean
);
```

- `scope_kind` 記四種範圍之一，值為 company、team、product、mgmt
- 範圍為 company 時 `scope_id` 填固定值
- 有效權限為該帳號全部 Role 的聯集
- **有效權限在讀取時計算，不預先展開:**
    - 預先展開會把整層項目固化成當下的 `Mgmt` 清單
    - 固化後新增的 `Mgmt` 不再自動涵蓋
    - 該行為與權限自動擴張的定案衝突

```sql
CREATE TABLE tag_group (
  name   text PRIMARY KEY,
  target text,
  system boolean
);

CREATE TABLE tag_value (
  group_name text,
  value      text,
  PRIMARY KEY (group_name, value)
);

CREATE TABLE view_share (
  view_id     uuid,
  target_kind text,
  target_id   uuid,
  share_level text,
  PRIMARY KEY (view_id, target_kind, target_id)
);
```

- `target` 記該標籤群組掛在帳號或 Role
- `view_share` 的 `target_kind` 值為 account、team、company

## 定案對範圍外工作的依賴

- 本篇範圍內的項目皆已定案
- **工作日與假日未設定:**
    - 偏離天數的計算基準是否扣除假日未定
- **檢視層僅盤點三種形態:**
    - 已盤開發順序表、看板、燃盡圖
    - 其餘形態未盤，可能帶出新的必帶欄位
- **對外分享未設計:**
    - 分享對象目前限公司內的帳號
    - 客戶自行檢視進度的需求須另行設計
- **權限異動的稽核未設計:**
    - Role 定義與分派的異動是否寫入變更歷史未定
    - 欄位變更歷史目前只涵蓋工單欄位
