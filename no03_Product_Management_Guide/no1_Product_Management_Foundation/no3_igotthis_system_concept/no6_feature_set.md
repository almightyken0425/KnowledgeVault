# 功能構想與痛點對應

> 本篇回答系統提供哪些功能、各自解掉哪個痛點。痛點清單與根因歸納見系統總覽篇，建議先讀。

## 痛點對應矩陣

- 痛點原文與工具現況見系統總覽篇的現況與痛點章節
- 對應程度分全解、部分解、裁決三類，績效類痛點的裁決獨立成章
- 全解：
  - 沒有甘特圖 → Gantt 功能直接補上，加依賴檢查與紅線警示
  - 人工同步會漏 → 單一資料模型後，同步環節整個消失
  - Priority List 靠 excel 維護 → Development List 拖放排序承接
  - branch 與 commit 對不到工單 → `Issue<.task>` 即 branch，關聯是機制本身
    - 現階段對應靠自定義欄位人工承載，掛勾自動化屬構想，見系統邊界與市場對照篇
- 部分解：
  - 追原始 spec → Epic 需求來源加其下 Task 帶 spec 的 commit
  - 解到 commit 級：找得到出貨當時那份文件，不必翻 code 也不必問人
  - 未解到條目級：哪一條規格被違反，仍需人打開該 commit 自行判讀
  - 這是檔位 C 的必然代價，系統不解析 git 內容
- 部分解的殘留細節：
  - bug 追溯要看 spec git 哪個 commit，與 Epic 需求來源的對照靠人工

---

## 績效類痛點的裁決

- 系統不做個人記點排名，只記客觀事實
- severity、來源、commit 關聯、工時全留存
- 報表預設團隊視角，個人判斷由主管質性進行
- 理由：指標變目標就失真，灌水痛點即證據
- 工時採人工填報，系統不做真實性驗證

## 功能清單

- 產品不含 AI 成份的細則與理由不在本篇，見系統邊界與市場對照篇
- 成本計算表的外部工具產出標記欄位，其行為細節同見該篇

### Development List 與 Gantt 合併面板

- 一體兩投影：拖放清單加時間軸
- 清單：多個 Epic 拖放排 priority，排序越前優先級越高
- 有無需求來源的 Epic 同列一張清單，兩者都佔人力
- 時間軸：同一批 Epic 與 Task 的排程投影
- 展開 Epic 可見母子單與 Epic 內的 subtask 前後關係
- 不同 Epic 的 subtask 在資料結構上不互相關聯
- 逐 Task 可開關排序檢查，異常顯示紅線，可強制系統重排
- 疊圖依據待決，系統讀不到 roadmap 內容，見風險與待決篇
- 一次開發可牽動多個平行項目，如 Promotion 重構動到 Promotion、Wallet、Notice
- 人員撞期屬管理政策，不是系統硬約束
- 面板提供篩選：找出同一時段持有多張工單的人
- 語意分工：清單承載意圖排序，時間軸承載推導排程，紅線呈現兩者矛盾

### 成本計算表

- 以人與商業產品兩個軸彙總
- 不切到模組層：共用元件被改時，成本歸屬講不清
- 人可跨商業產品，工時跟著 Task 走，Task 屬於哪個商業產品就記哪個
- 標記為外部工具產出的 Task 不計工時，成本表不涵蓋該代價
- 計算 BurnDownRate，納入休假與國定假日
- 工時來源：人工填報，由執行者自行填寫每張 Task 花費
- 不採系統推算，狀態時間差含等待與阻塞，不等於工作量

### TraceMap

- 每類工單連上一層
- 追溯鏈的完整結構與精度分級，見資料模型與追溯篇

### 自定義表單

- 自定義欄位掛在四組欄位容器內，可自訂名稱與 value 型別
- 欄位配置的範圍由 Team 承擔
- 階層是使用者工件內的文件約定，系統不配置也不感知
- 類型欄位區分 feature 與 bug，是 `Issue<.item>` 的自定義欄位例子
- branch 欄位填在母單或子單，由團隊自定義
- 維度即欄位，篩選規則見組織與泛型結構篇的欄位與篩選章節

### 使用者管理

- 國家、地區、聯絡方式、role
- 人隸屬 Company，可跨 Team 與 Product

### 工作日設定

- 按國家與縣市

### 關聯資料匯出

- 工單開出時，往對應 repo 的 branch 寫一份關聯資料檔
- 內容是系統已持有的關聯：需求列、repo 路徑、commit、測試案例
- 檔位 C 的工件只給 repo 路徑與 commit，不給內容片段
- 匯出的每一位元都來自使用者填在系統裡的資料
- 另提供查關聯圖的介接，使用者用自己的憑證
- 誰讀這份檔案、拿去做什麼，不在系統的認知範圍內
