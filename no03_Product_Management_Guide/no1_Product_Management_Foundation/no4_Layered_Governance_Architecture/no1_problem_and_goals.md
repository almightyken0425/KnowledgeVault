# 治理文件架構：問題與目標

> 產品管理文件系統的分層治理設計指南。本資料夾回答一個問題：如何規劃管理文件，讓結構變更只需改一處宣告，而非掃遍全庫。

---

## 案例：一次層重編號的實際代價

2026-07 ai-company 工作區執行過一次工件層重編號，範圍含 spec 與 design 目錄對調編號、新增品質與發布兩個獨立 git 層、專案管理目錄遷出產品。這次變更牽動約二十個 git repo、上百處引用，包括：

- 各 repo 說明文件內的路徑字串
- 自動攔截工具內的目錄名正則與編號字元類別
- 產品註冊表的路徑欄位
- 路由規則文件的層清單與連鎖表
- 長期記憶文件內的路徑與歸屬詞
- 四層與五層這類寫死的層數字樣，散落二十餘檔

變更本身的決策五分鐘，同步所有引用花費數十倍時間，且事後複驗仍抓出十餘處漏改與誤改。誤改中最典型的一類：批次替換把帶日期的歷史沿革句一併改寫，造成時代錯置。

---

## 根因分析

- **層模型沒有宣告處：** 沒有任何一份文件宣告現存工件層清單。層的存在散落在目錄名、正則、敘述文字中，彼此互為隱性複本
- **編號被當成身分：** 引用一個層時寫的是編號目錄名。編號一變，所有引用全部失效
- **層數寫進敘述：** 層數字樣把清單長度複製進每個提及的句子。加一層等於全庫搜補
- **註冊分散：** 新產品或新 module 要在註冊表、實體目錄、多份說明文件各登記一次，漏一處就出現配對缺口
- **產品形態被假設統一：** 敘述文件寫死一套結構，但實際上有的產品無設計層、有的純概念無實作層。差異靠 null 欄位默默表達，敘述與實況脫節
- **歷史與現況混寫：** 沿革句與現況句混在同一文件、無標記，批次工具無法區分

---

## 目標

- **單處宣告：** 層模型只在一份機器可讀的宣告檔存在。其他文件引用宣告檔、由宣告檔衍生、或受檢核器把關
- **編號可變、身分不變：** 每層有穩定識別碼。重編號只動宣告檔的呈現欄位，引用不失效
- **層數不落地：** 任何敘述文件不寫死層的數量與清單
- **單點註冊：** 新產品登記一次，其餘由宣告檔與形態設定推導
- **形態顯性化：** 不同產品形態對應不同層組合，用設定宣告而非 null 欄位默契
- **歷史可標記：** 沿革內容有明確區塊標記，批次工具自動繞過
